What the results mean: correctness, speed and expert memory

How to read the benchmark numbers, why terse prompts score higher, why more RAM barely helped GLM-5.3, and the caching experiments that come next.

1What we compare

The primary comparison is generation tokens per second alongside correctness, always shown with the prompt style, the setting, the number of graded answers and how many were cut off. Answer time and prompt-reading time are secondary: they explain how responsive a setting feels, but do not replace generation throughput. Rates for tiny outputs are noisy, and a change of prompt style is not an engine speed-up.

Busy machineAll timings come from the owner’s everyday 32 GB Apple M6 with other apps running, not a controlled machine. Real performance may be better.

2Did terse prompts improve quality?

They improved the measured automatic score. GLM-5.3 int4, exact, rose from 21/24 correct with normal answers to 24/24 with terse answers, while both averaged 0.41 generation tokens per second. This does not show that the model became more capable.

Why the score moves without the model changing:

    Use terse prompts for direct answers. To test general quality, give both styles enough output budget and review the answers independently, including the reasoning. Native Ollama runs also change sampling and thinking and allow 4,096 tokens, so they are not a controlled test of wording alone.

    3Why did extra GLM RAM barely help?

    The 18 / 22 / 26 GB budget sweep measured 0.4 / 0.41 / 0.42 tokens per second, with expert cache hits of 2.1 / 2.8 / 3.6%. Generation barely moved.

    The reason is in the logs. Even at 26 GB, the run reports a dynamic cache of one expert per layer (about 1.6 GB) plus 91 pinned experts (about 1.9 GB). The engine’s fast-SSD heuristic on Metal favours the operating system’s page cache and says to override the capacity with --cap. So these runs did not test a substantially larger expert cache, and they do not show that one would be useless.

    A RAM budget is not the memory actually kept for experts, and a logical cache miss is not proof of a physical SSD read: the page cache may serve it.

    4How could caching improve?

    1. Test actual capacity first. Explicit 1, 2, 4 and 8 experts per layer, a fixed pin set, no expert skipping, and a memory check before each run. Skip any capacity that is not safe.
    2. Keep useful experts. Frequency-aware admission or a protected hot set can stop one-use experts evicting repeatedly useful ones. Compare against LRU at the same retained bytes. A hypothesis, not a measured win.
    3. Allocate unevenly. Spend memory on the layers with the largest avoided read cost per byte. Pinning already exists; the experiment improves which experts are chosen.
    4. Test prefetch separately. A correct prediction can hide latency without improving cache hits. Count useful and wasted reads, and total time.
    5. Keep execution efficient. Avoid duplicate copies and repacking: OLMoE showed that better cache coverage alone does not remove transfer and packing overhead.

    Keeping the experts the model selects preserves its computation, though changed kernels can still change numeric output. Choosing different experts because they are in cache is a separate experiment that changes output, not an exact cache optimization. Judge every proposal by tokens per second and correctness; memory and bytes read are diagnostics, and a higher hit rate is not success on its own.

    5What is OLMoE?

    OLMoE is Allen AI’s open mixture-of-experts model: about 7B parameters in total, about 1B active per token. Our 4-bit copy is about 3.9 GB. It is the small testbed for the resident and streaming experiments. It is not Qwen, and its results do not establish a Qwen speed-up.
